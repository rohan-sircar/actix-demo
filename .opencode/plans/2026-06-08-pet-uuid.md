# Add pet_uuid to Pet Profiles

## Goal
Add a `pet_uuid` column to the `pets` table and expose it in the API. The `pet_id` (SERIAL) remains as the internal primary key, while `pet_uuid` is used for public-facing route parameters to avoid enumeration attacks.

## Changes

### 1. Migration: `migrations/2026-06-07-000000_create_pets/up.sql`

Add to `pets` table definition (after `id SERIAL PRIMARY KEY`):
```sql
pet_uuid UUID NOT NULL UNIQUE DEFAULT gen_random_uuid(),
```

Add index for lookups:
```sql
CREATE INDEX idx_pets_pet_uuid ON pets(pet_uuid);
```

The `pet_personality_traits.pet_id` FK stays as-is — it references the internal `pets(id)` for cascading deletes. The `pet_uuid` is purely for public API exposure.

### 2. Migration: `migrations/2026-06-07-000000_create_pets/down.sql`

```sql
DROP TRIGGER IF EXISTS trg_pets_updated_at ON pets;
DROP FUNCTION IF EXISTS update_pets_updated_at();
DROP TABLE IF EXISTS pet_personality_traits;
DROP TABLE IF EXISTS personality_traits;
ALTER TABLE pets DROP COLUMN IF EXISTS pet_uuid;
DROP TABLE IF EXISTS pets;
```

### 3. Models: `src/models/pets.rs`

#### New `PetUuid` newtype:
```rust
#[derive(
    Debug, Clone, Eq, Hash, PartialEq, Deserialize, Display, Into, Serialize,
    DieselNewType, Copy, ToSchema,
)]
#[serde(try_from = "String", into = "String")]
pub struct PetUuid(uuid::Uuid);
```

Implement `FromStr`, `TryFrom<String>`, `From<PetUuid> for String`, `From<PetUuid> for uuid::Uuid`.

#### Update `Pet` model:
Add `pub pet_uuid: PetUuid` field. Diesel `Queryable` derives struct-field-to-column-by-name mapping, so this will automatically pick up the new column.

#### Update `PublicPet` model:
Add `pub pet_uuid: PetUuid` field. Update the `From<(&Pet, Vec<PetTrait>)>` impl to include `pet_uuid: pet.pet_uuid`.

### 9. Edge Cases & Considerations

#### a) Existing data
Since this is a fresh migration (no existing data yet), `DEFAULT gen_random_uuid()` will handle all rows automatically. No data migration needed.

#### b) `pet_id` still in `PublicPet` response
The internal `id` field remains in `PublicPet` for backward compatibility and internal use. The `pet_uuid` is the new public-facing identifier. Clients should migrate to using `pet_uuid`.

#### c) Junction table `pet_personality_traits`
Stays unchanged — still references `pets(id)` (INTEGER). The junction table is internal infrastructure, not exposed in the API. No need to duplicate with UUID.

#### d) `PetId` newtype still used internally
`PetId` remains for internal operations (junction table lookups, Diesel queries on primary key). `PetUuid` is specifically for route parameters and public API responses.

#### e) `gen_random_uuid()` requirement
PostgreSQL 13+ has `gen_random_uuid()` built-in. The test container uses PostgreSQL 13 (`with_tag("13-alpine")`). If upgrading PG version in the future, confirm this function is still available (it is in all PG 13+ versions).

#### f) Diesel UUID support
The `uuid` feature is already enabled in Cargo.toml diesel dependencies. Diesel can directly deserialize `uuid::Uuid` columns. The `PetUuid` DieselNewType wrapper handles the type mapping.

#### g) Route parameter parsing
`PetUuid` implements `FromStr` via `uuid::Uuid::parse_str`, so `web::Path<PetUuid>` will auto-parse UUID strings from the URL path. Invalid UUIDs will return 400 Bad Request automatically.

#### h) Unique constraint
`pet_uuid` has a `UNIQUE` constraint. Since it's generated client-side (via `gen_random_uuid()` on the server at insert time), collisions are astronomically unlikely (1 in 2^122). No application-level collision handling needed.
