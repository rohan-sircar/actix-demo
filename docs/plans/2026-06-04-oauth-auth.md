# OAuth Authentication Integration

## Problem

Currently the app only supports email/password auth. User wants to add OAuth as the primary auth method (email auth kept as fallback for dev/local).

## Approach

Add OAuth 2.0 support for GitHub and Google using the `oauth2` crate. OAuth login creates/updates a user record and issues a standard JWT session cookie — the existing session flow stays untouched.

## Scope

### In scope
- GitHub OAuth (primary, easiest to integrate)
- Google OAuth (second provider)
- New DB migration: add `oauth_provider` + `oauth_uid` columns to users table
- New config fields for OAuth client credentials
- New routes: `/api/auth/oauth/{provider}/login`, `/api/auth/oauth/{provider}/callback`
- PKCE flow (no client_secret exchange in browser)
- Account linking: same email from multiple providers → same user record
- Auto-registration on first OAuth login
- Integration tests with mock OAuth server

### Out of scope
- Microsoft, Apple, or other providers
- OAuth2.1 / DPoP
- Social profile avatars (use existing avatar system)
- Email/password deprecation (email auth stays as fallback)

## Database Changes

### Migration: `2026-06-04-000000_add_oauth_to_users`

```sql
ALTER TABLE users
ADD COLUMN oauth_provider VARCHAR(32) DEFAULT NULL,
ADD COLUMN oauth_uid VARCHAR(128) DEFAULT NULL;

-- Unique constraint: a user can only have one OAuth account per provider
CREATE UNIQUE INDEX idx_users_oauth_provider_uid ON users (oauth_provider, oauth_uid)
WHERE oauth_provider IS NOT NULL;

-- Email stays the lookup key across providers
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

## Routes

### `/api/auth/oauth/github/login` (GET)
- Redirects user to GitHub's `/authorize` with `state` + `code_challenge` (PKCE)
- Stores `state` in Redis with 5-min TTL
- Returns 302 redirect

### `/api/auth/oauth/github/callback` (GET)
- Receives `code` + `state` from GitHub
- Validates `state` against Redis (prevents CSRF)
- Exchanges `code` for `access_token` + `id_token` via `oauth2::AuthorizationCode`
- Extracts user info: email, name, avatar URL
- Looks up user by email (existing lookup key)
  - If user exists and has matching OAuth provider → login
  - If user exists but different provider → account linking (update `oauth_provider` + `oauth_uid`)
  - If user doesn't exist → auto-register with OAuth info
- Issues JWT session cookie (same as email login)
- Returns 302 redirect to `/` or a configurable landing page

Same pattern for `/api/auth/oauth/google/login` and `/api/auth/oauth/google/callback`.

## OAuth User Flow

```
1. User clicks "Login with GitHub"
2. → GET /api/auth/oauth/github/login
3. → 302 Redirect to GitHub authorize page (with PKCE state)
4. User authorizes on GitHub
5. → GET /api/auth/oauth/github/callback?code=...&state=...
6. → Backend validates state, exchanges code for tokens
7. → Extracts user email from GitHub API
8. → Looks up user by email
   - Found + same provider → login (issue JWT)
   - Found + different provider → link account (update oauth_provider/uid)
   - Not found → auto-register user, issue JWT
9. → 302 Redirect to app landing page
```

## Security Considerations

- **PKCE**: Required for all OAuth flows (prevents authorization code interception)
- **State parameter**: Stored in Redis with short TTL, validated on callback
- **Email verification**: OAuth users are auto-verified (provider already verified the email)
- **No password stored**: OAuth users have no bcrypt hash — login only works via OAuth
- **Account linking**: Same email from different providers merges into one user (by email uniqueness)
- **Client secrets**: Never exposed to browser — all token exchange happens server-side

## Testing Strategy

- Integration tests with `wiremock` to mock GitHub/Google OAuth endpoints
- Test happy path: login → redirect → callback → session
- Test state validation: invalid state → 403
- Test account linking: same email, different provider → same user
- Test auto-registration: new email → creates user
- Test expired state: state past TTL → 403
